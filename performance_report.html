🔬性能拐点分析

全表查询 严重

拐点：1,000 → 5,000 条
数据增长：5.0 倍
耗时增长：8.8 倍（43ms → 381ms）
10万条：4,741ms（接近5秒）
原因：SELECT * 返回全部字段 + ORDER BY 排序，无分页限制

模糊搜索（LIKE） 警告

拐点：10,000 → 50,000 条
数据增长：5.0 倍
耗时增长：3.3 倍（18.6ms → 60.9ms）
10万条：136.7ms
原因：LIKE '%keyword%' 无法使用索引，需全表扫描

单条查询（主键） 优秀

拐点：无明显拐点
全程稳定：0.75ms ~ 0.96ms
10万条：0.77ms
原因：主键索引直接定位，时间复杂度 O(logN)

COUNT统计 警告

拐点：10,000 → 50,000 条
数据增长：5.0 倍
耗时增长：5.4 倍（3.5ms → 19.2ms）
10万条：26.2ms
原因：COUNT(*) 需遍历全表统计行数

💡优化建议

  • 【高优先级】全表查询加分页：当前 SELECT * 一次返回全部数据，5000条时已达381ms。 建议添加 LIMIT + OFFSET 分页，每页控制在50条以内，可将响应时间降至10ms以下。
  • 【高优先级】避免 SELECT *：只查询列表需要展示的字段（如 name, student_no, age）， 减少数据传输量和内存占用。
  • 【中优先级】模糊搜索优化：LIKE '%keyword%' 无法走索引。建议对 name 和 student_no 添加全文索引（FULLTEXT），或引入 Elasticsearch 实现高效搜索。
  • 【中优先级】COUNT缓存：学生总数不需要实时计算，可用 Redis 缓存或定时任务更新统计值， 避免每次请求都全表扫描。
  • 【低优先级】添加数据库索引：为 is_deleted 字段添加索引，加速软删除过滤条件： CREATE INDEX idx_is_deleted ON students(is_deleted);
